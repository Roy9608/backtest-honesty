# 附录：代码变更前的三审制

**AI 无法自证正确，所以必须把"检查"变成流程，而不是依赖"这次我注意一点"。**

---

## 为什么需要它

一个真实项目里，**一天内出现 7 个 bug、6 次归因错误**。

其中大部分本可以被这套流程挡住：

| 错误 | 哪一步能挡 |
|---|---|
| 滚动求和原地读写 | ① 数据流完整性 |
| 变量未传入函数 | ① 数据流完整性（实操中抓到） |
| 阈值加错了基准值 | ④ 边界与异常 |
| β 逐笔相加虚高 | ① 数据流完整性 + ⑥ 可验证性 |
| 同参数两跑结果不同 | ⑥ 可验证性 |

---

## 五步（必须走完才动代码）

```
① 方案自评 → ② 提升一轮 → ③ 再自评 → ④ 情况说明 → ⑤ 才动代码
```

### 评分卡

满分 60 分。**低于 48 分（80%）判不及格，必须提升一轮。**
两轮评分必须说明**提升在哪**。

---

## 自评六项检查

| # | 检查项 | 说明 |
|---|---|---|
| 1 | **数据流完整性** | 变量从哪来、到哪去、断点在哪、**所有调用点是否都改** |
| 2 | **改动面与波及** | 签名变更时，跨文件搜全部调用点 |
| 3 | **状态与生命周期** | 初始化 / 重置 / 残留 / 重启 |
| 4 | **边界与异常** | None / 0 / 空 / 异常不崩主循环 |
| 5 | **不变量与副作用** | 有没有破坏既有假设 |
| 6 | **可验证性** | 具体命令 + 期望输出 + 回滚方案 |

### 关于第 5 项：不变量要显式列举

**对交易系统，至少三条**：

1. **一次只能持一仓**
2. **成本已扣**
3. **无未来函数**

> **不变量要显式列举，不能靠"我记得"。**

---

## 情况说明固定 7 项

1. **改什么**
2. **为什么**
3. **改哪几处**（文件 + 行号）
4. **风险等级 + 最坏情况**
5. **怎么验证**（可复制命令）
6. **怎么回滚**
7. **我不确定的地方**（**硬要求，不许隐瞒**）

### 关于第 7 项

这一项是最容易被省略的，也是最有价值的。

> **如果 AI 或协作者说"没有不确定的地方"，这本身就是可疑信号。**

---

## 两道防呆：语义自检

新增规则类型时，加**逐位等价检查**，防止新代码写歪：

```python
# 例：新规则 struct_hw(N=70, p=999) 应当在语义上等价于已知规则 swing_low(70)
assert 逐位相同(新规则(70, 999), 已知规则(70))   # 66 笔 vs 66 笔，逐位对比
```

> **新代码写歪时，程序通常不报错，结果只是"不太一样"。**
> **语义自检能在跑完全部实验之前抓住它。**

---

## 配套：静默降级的防呆

一个真实教训：`backtest()` 的默认参数是 `ticks=5`，
导致未显式传 `ticks` 的调用会把"8bp"悄悄变成"5tick"。

**修法**：

```python
def backtest(..., ticks=None):
    if 限价模式 and ticks is None and bp is None:
        raise ValueError("限价模式必须显式指定 ticks 或 bp")
```

> **默认值是有害的 —— 它让"忘了传参数"变成一个静默的错误。**
