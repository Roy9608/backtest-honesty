# 铁律 6：文档交付前必须做「语义一致性」检查

**只查结构是不够的。** 结构检查（重复标题、乱码）过得去，内容可能已经自相矛盾。

## 事故经过

一个迭代很快的项目，结论在一天内被推翻三次：

```
不成立  →  找到死穴  →  是 β 不是 α  →  当前形态可用
```

**每次修正都只改了「新位置」，忘了回头清理「旧位置」。** 结果：

| 文档 | 残留的旧结论 | 位置 |
|---|---|---|
| 待续卷 | "α 小于成本，直觉不够" | 开篇 / 概述 / 附录 |
| 白皮书 | "策略：未通过验证，不上实盘" | 正文两处 |

**读者读到附录时直接问**："这句话啥意思？我的参数不是都很合理吗？"
—— 他看到的是一句**早被推翻的旧结论**。

## 为什么危险

**旧结论往往写得比新结论更"具体"** —— 有数字、有比喻、有画面感。
读者（包括三个月后的自己）会**优先相信那句更抓眼的**。

**而且它是隐性矛盾**：两份结论都在文档里，
没有报错，没有乱码，结构检查全绿。

## 交付前必做（三项）

| # | 检查 | 做法 |
|---|---|---|
| 1 | **结构** | 章节齐全、无重复标题、无乱码 |
| 2 | **★ 语义一致性** | 搜索**所有被推翻的数字/结论**，确认每一处要么删除、要么明确标注「已推翻」 |
| 3 | **单一真相源** | 文档只保留**一个**结论区；历史保留在「账本/教训」章节，不留在结论区 |

## 实用做法

```python
# 把「被推翻的结论」列成清单，全文扫描残留
stale = ['旧结论关键词1', '旧数字2', '旧表述3']
for k in stale:
    n = src.count(k)
    if n:
        print(f'残留 [{k}] x{n}')     # 必须逐处确认
```

## 多版本文档的额外要求

**v1.0 → v2.0 的文档，必须在开头加「阅读提示」，写明哪个章节是最终结论。**

否则读者可能停在中间某一版。

一个可行的做法：
- 文档开头注明「**若章节冲突，以章节号大者为准**」
- 被推翻的章节顶部加「⚠️ 已被 §N 推翻」横幅

## 一句话

> **文档不是一次写完的。每次修正，都要回头把旧的清干净。**
